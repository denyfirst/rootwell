# Review of Rootwell — 22 November 2026

This review covers `main` at `b8bfa5f` (PR 118). The new maintainer made it
before taking the project over. It looked at four areas, reading the code end
to end:

- the web gate and sign-in;
- data at rest;
- the network code;
- the browser code and the supply chain.

Each finding below was traced in the code. The time and capacity findings were
also reproduced in a throwaway test. This is not the independent release audit
that `ENGINEERING.md` requires before a release.

**Local evidence at that commit:**
- `go build`, `go vet` and `gofmt` were clean.
- The tests of 42 packages passed on Windows. Linux-only tests run in CI.

Each finding's **Status** says whether it is fixed, or which phase of
`PRODUCT-PLAN.md` removes it.

## Summary

- **Critical:** nothing.
- **High:** one finding. The store locks for good after about 5,120 writes.
- **Medium:** five findings.
  - The session cookie reaches other `localhost` services.
  - The IPv6 loopback port can be taken.
  - The data key never changes.
  - `.dockerignore` is too broad.
  - ACME has never run against a real CA.
- **Low and Info:** the rest.

The core engineering is careful, and much of it stays. It is listed at the
end.

The larger problems are in the product:

- It cannot obtain a certificate a browser trusts.
- Renewal runs only while someone is signed in.
- Nothing delivers a certificate to a server.
- The pages ask for the password 13 times and carry about 3,600 words of
  text, mostly caveats.

### RW-01 — Lifetime write limit (High)

Every write adds one history event: an import, a note, a deletion, a DNS step
or a renewal.

- At most 1,024 events stay active (`internal/inventorystore/history.go`).
- At most 4 archive pages exist, and an archive needs at least 512 active
  events (`history_archive.go`).
- Events must be consecutive.

After about 5,120 writes, every write fails with a limit error, and nothing
resets it. That includes:

- deleting a private key;
- removing the Cloudflare token;
- every renewal.

Renewal already pauses once fewer than 320 events remain
(`renewal_cycle.go`). The history is not audit evidence (`history.go`). It
should never stop a write.

Phase 1 deliberately leaves the old store alone. Making its history roll
over would touch the capacity reservations of every ACME step, and Phase 3c
removes those steps. No installation exists yet. The Phase 3b store keeps a
rolling history that never refuses a write.

Fixed in Phase 3a, part 2: the old store and its history are gone, together
with the ACME steps that reserved capacity in it. Certificates live in the
vault (`internal/vault`, `internal/certstore`), where a write adds no history
event and nothing counts toward a lifetime limit. The list holds at most 500
certificates (`TestTheListStopsAtItsLimit`); a page that read an older
generation gets 409
(`TestSaveListsTheCertificateAndRefusesAStalePageOrADuplicate`).

### RW-02 — The cookie is shared by every localhost port (Medium)

The session cookie is set for the host `localhost`. Browsers do not separate
cookies by port, and they send Secure cookies to `http://localhost`. Any other
local web server the user opens therefore receives a 12-hour session token.

A local process can replay that token with forged headers. With it, it can:

- read the inventory;
- run website checks;
- delete records together with their keys (see RW-10).

Interim fix: serve on its own name, `rootwell.localhost`. The lasting fix is
HTTPS on its own name in Phase 3a.

### RW-03 — The IPv6 loopback port can be squatted (Medium)

`rootwelld` listens only on `127.0.0.1:4180` (`cmd/rootwelld/main.go`).
Browsers often try `[::1]` first for `localhost`. On a host shared with other
accounts, another account can listen on `[::1]:4180` and collect the password.

Fix: also listen on `[::1]:4180`, and refuse to start if either address is
taken.

Fixed: `listenLoopback` in `cmd/rootwelld/main.go` holds both addresses and
refuses to start when the IPv6 port is taken. `TestListenLoopbackHoldsBothAddresses`
and `TestListenLoopbackRefusesATakenIPv6Port` cover both cases.

### RW-04 — The data key is never rotated (Medium)

Changing the password, rotating the recovery code and a recovery reset all
re-wrap the same data key (`internal/instanceaccess/access.go`,
`recovery_enroll_core.go`). An old access file or snapshot, together with the
old password or code, therefore still opens today's and tomorrow's data.

Phase 3a introduces an instance key with rotation.

Since Phase 3a, part 3, there is no access file, snapshot or password that
opens data: the instance key opens the vault (part 2), and the password only
signs in. The instance key itself is not rotated yet, so an old copy of the
data directory with today's key, or its recovery code, still opens; key
rotation comes in Phase 3b.

### RW-05 — `.dockerignore` re-includes whole trees (Medium)

`!cmd/`, `!internal/` and `!web/workbench/` bring every file under them into
the build context, not only the source files the comments describe. Only
`*.pem` is excluded again.

The runtime image copies all of `web/workbench/`. A stray `.key`, `.pfx` or
`.env` there would ship inside the image.

Fix:
- re-include files, not directories;
- copy an explicit list of assets;
- test what actually reaches the build context.

Fixed: `.dockerignore` now names files only. `scripts/test-build-context.sh`
builds the real context from a copy of the commit with planted `.key`, `.pfx`,
`.env` and `.pem` files, and fails on anything outside the reviewed list.
`scripts/test-container-config.mjs` refuses a directory exception, and refuses
a missing asset the gate requires.

### RW-06 — ACME is untested live and fails on small surprises (Medium)

- The directory check rejects the whole directory if any optional endpoint
  has an unexpected path (`internal/acmestaging/directory.go`).
- A `badNonce` answer, which RFC 8555 expects clients to retry, ends the
  operation.
- No run against the real Let's Encrypt staging server is recorded.

The renewal engine of Phase 3c retries `badNonce` once and treats optional
endpoints as optional. Phase 4 runs it live.

### RW-07 — The attempt limiter counts successes and is global (Low)

Five attempts a minute are shared by sign-in, password change and every
password re-check, and successful attempts count too (`cmd/rootwelld/gate.go`).
Even a "busy" answer uses an attempt.

This has two effects:
- Any local process can keep the owner out.
- One manual ACME run exceeds the budget by itself.

Fix: count failures only, and give each purpose its own budget.

Fixed in Phase 3a, part 3: wrong passwords and codes count against the
account name (5) and the source address (20, IPv6 by its /64), then each
further failure doubles a wait from one minute up to fifteen. A success costs
nothing, a busy answer is not a failure, and wrong setup codes have a limit
of their own (`cmd/rootwelld/session.go`,
`TestOnlyFailuresCountPerNameAndPerSource`,
`TestAFullFailureTableHoldsNewNamesRatherThanForgetALock`). Nothing else asks
for the password again, so no re-check draws on the limit.

### RW-08 — The key-derivation slot is held across network calls (Low)

Renewal, timing, order and DNS operations hold the password-derivation slot
across up to 25 seconds of CA or Cloudflare calls. During that time, sign-in
answers "busy" and still uses an attempt.

Phase 3a separates the two locks.

Fixed in Phase 3a: the renewal, timing, order and DNS operations went with
part 2, and nothing that reaches the network takes the slot now. It guards
only local work: password checks and the Certificates page's file checks.
Since part 3 a request waits up to five seconds for it, and a busy answer
uses no attempt (RW-07).

### RW-09 — Password limits differ (Low)

A password of up to 1,024 bytes can be set and used to sign in. Every
re-check, however, refuses more than 256 bytes. A long passphrase can
therefore never download a key or run an ACME step.

Fix: one shared limit.

Fixed in Phase 3a, part 3: setting, signing in and changing a password all
use one limit, 1,024 bytes (`account.MaxPasswordBytes`,
`TestPasswordsHashAndVerifyWithOneLimit`). The password re-checks are gone:
downloading a key needs a fresh phone code instead.

### RW-10 — Delete removes the private key without asking for the password (Low)

Deleting a record also deletes its attached private key
(`internal/inventorystore/manifest.go`). The confirmation text says it
"removes only the current inventory record", and no password is asked.

Fix:
- say that the key is deleted too;
- ask for the password when the record has a key.

Fixed in Phase 3a, part 3: deleting a certificate that has a saved key needs
a phone code from the last ten minutes. Without one the server answers 428
and deletes nothing, and the page asks for a code
(`TestLinuxCertificatesLiveInTheVaultAndSurviveARestart`). A certificate
without a key is deleted without one
(`TestLinuxACertificateWithoutAKeyIsDeletedWithoutAFreshCode`).

### RW-11 — Every read opens every secret; core dumps are allowed (Low)

Each read decrypts every private key, both account keys and the Cloudflare
token, and the page monitor reads once a minute. Copies are left in buffers
that are never cleared, and nothing turns off core dumps.

Fix:
- Phase 1 turns core dumps off.
- Phase 3b opens a secret only when it is used.

Core dumps fixed: `hardenProcess` sets `RLIMIT_CORE` to zero and makes the
process non-dumpable before any subcommand runs.

Opening on use fixed in Phase 3a, part 2: a private key is a vault record of
its own. Listing reads certificate records only; a download borrows the key
for one use and clears it (`TestAKeyIsSavedApartAndOnlyALoanOpensIt`). The
account keys, the Cloudflare token and the page monitor are gone with the old
automation.

### RW-12 — Fingerprints are plaintext record IDs (Low)

Record IDs are the SHA-256 of the certificate, which is its public
fingerprint. Anyone holding a backup can look the fingerprints up in
Certificate Transparency logs and learn every managed domain.

Phase 3b uses keyed IDs.

Fixed in Phase 3a, part 2: vault record IDs are HMACs of the fingerprint
under a key derived from the instance key, and differ between installations.
No fingerprint or name reaches the database file
(`TestIndexesDifferBetweenVaultsAndKinds`,
`TestNoPlaintextOrNameReachesTheDisk`).

### RW-13 — An older image can be swapped in unnoticed (Low)

Only the access file is tracked. An older inventory file, or an old snapshot
restored elsewhere, can bring back deleted keys or a removed token.

Phase 3b records the store's generation under the instance key. Full
protection needs an outside anchor, which is a documented limit.

### RW-14 — PBKDF2 instead of Argon2id, with a fixed cost (Low)

PBKDF2-SHA256 with 600,000 rounds meets today's minimum. The file format
requires exactly that number, though, so the cost can never be raised.

Phase 3a uses Argon2id, as Keybash does.

Fixed in Phase 3a, part 3: the PBKDF2 access file is gone. Account passwords
are Argon2id hashes (64 MiB, three passes, four lanes) in each account's vault
record, with a version number so the cost can be raised later
(`internal/account`, `TestPasswordsHashAndVerifyWithOneLimit`).

### RW-15 — Pages claim protections that do not exist (Low)

- **"Loading signed build assets":** nothing checks a signature.
- **"No certificate uploads":** shown as a global badge, while Certificates
  uploads certificates and keys to the daemon.
- **"A temporarily encrypted key" goes to the server:** the random password
  travels in the same request, so the server receives the key itself. On
  loopback this is acceptable, but the sentence is wrong.

Fix: correct the wording.

Fixed: the wording now matches what happens. "Files stay in this browser" and
"Loading the local engine" replace the first two claims. The PFX note now says
the certificates and the key go to your own Rootwell. The delete confirmation
now says it deletes the private key too.

### RW-16 — Leaving the window wipes typed passwords (Low)

Some fields clear themselves when the window loses focus. Opening a password
manager or the file chooser does exactly that, so typed passwords disappear.

Fix: keep the clearing for a revealed key only.

Fixed: the request form clears its passwords when the page is left or hidden,
not when the window loses focus. A revealed key still hides on blur.

### RW-17 — One download revokes its URL at once (Low)

The old Certificates page script (removed on 22 November 2026) revoked the
download's object URL right after the click. Firefox has failed such
downloads. The other modules wait.

Fixed: it waits 30 seconds, as the other modules do.

### RW-18 — Website check reaches public addresses used internally (Low)

The address policy is thorough: it rejects private, loopback, link-local,
CGNAT, ULA, mapped, NAT64, 6to4, Teredo and reserved addresses. A public
address used inside a company, or a cloud provider's public service address,
still passes.

The impact is a TLS handshake to port 443 for a signed-in user. An optional
deny list for the operator comes later.

### RW-19 — Website check gives a generic failure for common misconfigurations (Low)

All of these end in "the check could not complete" instead of a named
problem:
- a duplicate certificate in the served chain;
- more than ten certificates;
- TLS older than 1.2;
- RSA key exchange only.

### RW-20 — Private-key functions are exported to every page (Info)

The WebAssembly module registers its key and PFX functions on every page.
Today, only the single-use workers call them.

Fix: register those functions only inside a worker.

### RW-21 — The 8.4 MB WebAssembly file is never cached (Info)

It is served and fetched with `no-store`, so every page load downloads and
compiles it again. Caching it under a versioned, hashed name is safe.

Fixed: the engine and its runtime are sent with `Cache-Control: no-cache`. The
browser keeps them and asks again with If-Modified-Since. Every other response
stays `no-store`.

### RW-22 — CI gaps (Info)

- The weekly vulnerability watch scans only the default platform.
- Fuzz crashers are not kept as artifacts.
- Jobs have no time limits.
- `cancel-in-progress` can cancel a run on `main`.

Fixed:
- The weekly watch also scans the WebAssembly build.
- A failing fuzz input is printed in the log.
- Every job has a time limit.
- Only pull-request runs are cancelled.

### RW-23 — Dependencies are behind (Info)

| Module | In use | Available |
|---|---|---|
| `golang.org/x/crypto` | 0.57.0 | 0.59.0 |
| `software.sslmate.com/src/go-pkcs12` | 0.7.3 | 0.7.4 |
| Go | 1.26 | 1.27 |

Keybash is on Go 1.27.

Fixed: Go 1.27.4, with the build image pinned by digest. `x/crypto` 0.59.0,
`go-pkcs12` 0.7.4 (one change: an explicit NULL parameter for the PBKDF2 PRF,
which the PFX preflight already accepts), and staticcheck 0.8.2, gosec 2.30.0
and govulncheck 1.9.0, as in Keybash.

## Product gaps found in the same review

- **ACME is fixed to Let's Encrypt staging.** No browser-trusted certificate
  can be obtained or renewed.
- **Automatic renewal is not automatic.** It is a job tied to a browser
  session. It pauses at 12 hours, at sign-out and at a restart.
- **Nothing delivers certificates.** No files are written and no server is
  reloaded.
- **Access is limited.** The service is loopback-only HTTP; a server needs an
  SSH tunnel. There is no MFA, and there are no accounts or roles.
- **Backups are offline only.** The service must be stopped, and both the
  password and the recovery code must be at hand.
- **Durable storage is turned off on Windows.**
- **There is no release or install script.**
- **The pages are hard to use:**
  - The Automation page has 14 confirmation boxes, 10 password fields and
    about 2,000 words.
  - Sign out is on one page only.
  - Internal terms reach the user, such as "generation", "atomic batch" and
    "07 / EXPLICIT RECORD DELETION".

## What is done well and stays

- **Requests:**
  - exact Origin, a custom header and Fetch Metadata on every request;
  - no CORS;
  - a strict CSP with no inline script;
  - `frame-ancestors 'none'`;
  - no `innerHTML` anywhere.
- **Sessions:** 256-bit tokens stored only as hashes, in a `__Host-`,
  HttpOnly, SameSite=Strict cookie. A password change ends every session.
- **Sealing:** AES-256-GCM with random nonces, bound to the installation, the
  record and the generation, with separate keys per purpose.
- **Files:** every file operation goes through `os.Root` and checks identity,
  owner and mode. Writes are atomic with `fsync`. Nothing is overwritten
  silently.
- **Network:**
  - fixed hosts at three layers for the CA and Cloudflare;
  - the dialled address is the checked address;
  - no redirects and no proxy;
  - strict, size-limited parsing of every answer.
- **Website check:** size and time limits, and a separate verification after
  the handshake.
- **Inputs:** bounded parsers with fuzz targets, single-use workers for keys
  and PFX files, and caps on encrypted-key and PFX work.
- **CI:**
  - no third-party actions;
  - permissions denied by default;
  - commit signatures checked against the base branch's signer list;
  - a base image pinned by digest;
  - a non-root, read-only runtime image.
